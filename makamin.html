MAKĀMIN: Fraud Detection

A fraud model that ranks risky transactions, explains each alert and shows the linked cards, emails and devices behind it, built on 590,540 real e-commerce transactions.

  • Machine learning
  • Network analysis
  • Dashboard
590,540real e-commerce transactions, 3.5% fraud
0.521average precision, 15× better than random
74%of fraud caught at the reference threshold
0.909ROC-AUC on later, unseen data

The problem

Only about 3.5% of transactions are fraud, so a model can look accurate while catching almost none of it. Fraud also rarely comes alone: the same card, email or device shows up across several transactions, which a model looking at one transaction at a time can miss. And an alert is only useful if an investigator can see why it was raised.

My role

Data Science Bootcamp capstone (Saudi Digital Academy × WeCloudData), team of 4. I led the modelling.

  • Python
  • XGBoost
  • TensorFlow/Keras
  • SHAP
  • NetworkX
  • Streamlit
  • Plotly

How I approached it

  1. Split by timetrain on earlier data, test on the last 118,108 transactions
  2. Link24-hour activity per card, address, email and device
  3. ModelXGBoost vs a neural network, with class weights
  4. ExplainSHAP reasons in a Streamlit dashboard

What I found

My part

The model ranks fraud 15 times better than chance.

On transactions it had never seen, average precision reached 0.521, against 0.034 for random guessing, with ROC-AUC 0.909. Splitting by time instead of at random keeps the test honest: the model never learns from the future.

Catching more fraud means more alerts to review.

At the 0.50 reference threshold the model caught 3,014 of 4,064 frauds (74%) but raised 14,122 alerts, so about 1 in 5 alerts is real fraud. Where to set the threshold is a business decision about how many alerts the team can review.

Fraud shows up in connected groups.

Linking transactions that shared a card, address, email or device in the previous 24 hours exposed coordinated activity, such as 35 linked transactions on one card in 73 hours. The map shows one case: the selected transaction (purple) linked to 168 earlier ones, 6 of them known fraud (red).

Inside the dashboard

Recommendation

  1. Set the threshold by team capacityDecide how many alerts investigators can review, then tune the threshold to it.
  2. Review linked cases togetherShared cards, emails and devices point to groups, not single events.
  3. Show the reason with every alertSHAP explanations let investigators check the score, not just trust it.

Limits

Limits: Public e-commerce data (IEEE-CIS), not Saudi bank records. 0.50 is a reference threshold, not a tuned production setting, and shared entities are signals, not proof of fraud.
